# 缺陷管理规程

## 目的

规范缺陷的提交、分类、处理、验证和关闭流程，确保缺陷得到及时有效的处理。

## 缺陷分类

### 严重等级

| 等级 | 定义 | 示例 | 修复时效 |
|------|------|------|---------|
| P0 - 致命 | 系统崩溃、数据丢失、安全漏洞 | 数据库损坏、未授权访问 | ≤ 4 小时 |
| P1 - 严重 | 核心功能不可用、影响大量用户 | 登录失败、支付失败 | ≤ 24 小时 |
| P2 - 一般 | 非核心功能异常、影响部分用户 | 搜索结果不准确、导出格式错误 | ≤ 72 小时 |
| P3 - 轻微 | 界面显示问题、不影响功能 | 文案错误、样式错位 | 下个版本修复 |

### 缺陷类型

| 类型 | 说明 |
|------|------|
| 功能缺陷 | 功能行为与需求不符 |
| 性能缺陷 | 响应时间、吞吐量不达标 |
| 安全缺陷 | 安全漏洞、权限绕过、数据泄露 |
| 兼容性缺陷 | 特定环境/浏览器/设备下异常 |
| 界面缺陷 | UI 显示与设计稿不符 |

## 缺陷生命周期

```
新建 → 确认 → 处理中 → 已修复 → 验证中 → 已关闭
  │       │       │                    │
  │       │       │                    └→ 重新打开 → 处理中
  │       │       └→ 延期
  │       └→ 拒绝（非缺陷/重复）
  └→ 取消
```

### 状态说明

| 状态 | 说明 | 可转换到 |
|------|------|---------|
| 新建（New） | 缺陷刚提交 | 确认、取消 |
| 确认（Confirmed） | 经确认为有效缺陷 | 处理中、拒绝、延期 |
| 处理中（In Progress） | 开发者正在修复 | 已修复 |
| 已修复（Fixed） | 开发者完成修复 | 验证中 |
| 验证中（Verifying） | 质量工程师验证修复 | 已关闭、重新打开 |
| 已关闭（Closed） | 验证通过 | — |
| 重新打开（Reopened） | 验证失败，需要重新修复 | 处理中 |
| 拒绝（Rejected） | 确认为非缺陷或重复 | — |
| 延期（Deferred） | 确认有效但当前版本不修复 | 处理中 |
| 取消（Cancelled） | 提交者主动取消 | — |

## 缺陷提交规范

### 必填字段

| 字段 | 说明 |
|------|------|
| 标题 | 简明描述问题，格式：`[模块] 问题概述`，如 `[认证] 用户登录后未跳转首页` |
| 严重等级 | P0 / P1 / P2 / P3 |
| 缺陷类型 | 功能 / 性能 / 安全 / 兼容性 / 界面 |
| 复现步骤 | 逐步描述如何复现问题 |
| 预期结果 | 正确行为描述 |
| 实际结果 | 实际发生的错误行为 |
| 环境 | 浏览器、操作系统、版本号 |
| 附件 | 截图、日志、录屏 |

### 提交要求

- 一个缺陷只描述一个问题
- 复现步骤必须可重复
- 严重等级按定义客观评定，不因修复压力降级

## 修复时效

| 等级 | 修复时效 | 超时处理 |
|------|---------|---------|
| P0 | ≤ 4 小时 | 立即升级到技术负责人 |
| P1 | ≤ 24 小时 | 每日跟踪，超时升级 |
| P2 | ≤ 72 小时 | 迭代内跟踪 |
| P3 | 下个版本 | 计划排期 |

## 发布前缺陷清零规则

- 发布时 P0 和 P1 缺陷必须清零
- P2 缺陷遗留数量 ≤ 5 个，且每个有明确的延期理由
- P3 缺陷可遗留，但需在发布说明中记录

## 缺陷分析

### 定期分析

- **每周**：缺陷趋势分析（新增/关闭/遗留）
- **每月**：缺陷根因分析（按模块、类型、根因分类）
- **每季度**：缺陷逃逸分析（生产缺陷占比和原因）

### 分析维度

- 按模块分布：识别缺陷高发模块
- 按类型分布：识别系统性薄弱环节
- 按根因分类：需求不清 / 设计缺陷 / 编码错误 / 环境问题
- 逃逸分析：哪些缺陷本应在测试阶段发现

## 度量

| 指标 | 目标值 |
|------|--------|
| 缺陷修复时效达标率 | ≥ 95% |
| 缺陷逃逸率 | ≤ 10% |
| 发布时 P0/P1 缺陷数 | = 0 |
