# 测试策略

## 概述

本文件定义全流程测试分层策略、各层覆盖要求和责任归属。测试策略由质量确认环节统一制定，各层测试在对应环节执行。

## 测试分层

```
┌─────────────────────────────┐
│         E2E 测试             │  ← 质量确认环节执行
├─────────────────────────────┤
│        集成测试              │  ← 质量确认环节执行
├─────────────────────────────┤
│        单元测试              │  ← 开发构建环节执行
└─────────────────────────────┘
```

### 单元测试（Unit Testing）

- **执行环节**：开发构建
- **执行者**：开发者
- **目标**：验证单个函数/方法/类的行为正确性
- **覆盖要求**：
  - 行覆盖率 ≥ 80%
  - 核心领域逻辑覆盖率 ≥ 95%
  - 所有公共 API 必须有测试
- **运行时机**：每次提交自动运行（CI）
- **命名规范**：`should_预期行为_when_条件`

### 集成测试（Integration Testing）

- **执行环节**：质量确认
- **执行者**：质量工程师 / 开发者
- **目标**：验证模块间交互、外部服务集成、数据持久化的正确性
- **覆盖要求**：
  - 所有限界上下文间的集成点有测试
  - 所有外部服务调用有契约测试
  - 数据库读写有集成测试
- **运行时机**：每日构建 + 发布前
- **环境**：独立测试环境，使用测试数据库和 Mock 外部服务

### E2E 测试（End-to-End Testing）

- **执行环节**：质量确认
- **执行者**：质量工程师
- **目标**：从用户视角验证完整业务流程
- **覆盖要求**：
  - 覆盖核心业务流程（P0 场景 100%）
  - 覆盖关键用户路径（P1 场景 ≥ 80%）
  - 覆盖跨系统交互场景
- **运行时机**：发布前必须执行
- **环境**：类生产环境（Staging）

## 专项测试

### 性能测试

- **执行环节**：质量确认
- **触发条件**：版本发布前、性能敏感功能变更后
- **详见**：[性能测试规程](performance-test-procedure.md)

### 安全测试

- **执行环节**：质量确认
- **触发条件**：每次发布前、安全敏感变更后
- **详见**：[安全测试规程](security-test-procedure.md)

## 自动化测试策略

### 目标

自动化测试占比 ≥ 60%

### 自动化优先级

1. **必须自动化**：单元测试、API 集成测试、核心流程 E2E 测试
2. **推荐自动化**：数据驱动的测试、回归测试
3. **手动测试**：探索性测试、可用性测试、复杂交互场景

### 技术选型

| 测试层级 | 推荐工具 | 说明 |
|---------|---------|------|
| 单元测试 | Jest / Vitest | 前端单元测试 |
| 单元测试 | JUnit / pytest | 后端单元测试 |
| API 测试 | Postman / Supertest | 接口集成测试 |
| E2E 测试 | Playwright / Cypress | 浏览器端到端测试 |
| 性能测试 | k6 / JMeter | 负载和压力测试 |
| 安全测试 | OWASP ZAP / Snyk | DAST / SCA |

## 测试与质量门禁的关系

| 门禁 | 相关测试 | 通过条件 |
|------|---------|---------|
| 开发构建门禁 | 单元测试 | 覆盖率 ≥ 80%，全部通过 |
| 质量确认门禁 | 集成测试 + E2E | 全部通过，P0/P1 缺陷清零 |
| 发布门禁 | 性能测试 + 安全测试 | 指标达标，无高危漏洞 |

## 度量

| 指标 | 定义 | 目标值 |
|------|------|--------|
| 自动化测试占比 | 自动化用例数 / 总用例数 | ≥ 60% |
| 测试用例通过率 | 通过数 / 执行数 | ≥ 98% |
| 缺陷逃逸率 | 生产缺陷 / (测试缺陷 + 生产缺陷) | ≤ 10% |
