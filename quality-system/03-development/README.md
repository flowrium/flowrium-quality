## 环节目标

高质量地实现设计意图。开发构建包含单元测试——验证前置，测试是开发的一部分。

## 质量验证机制

在开发构建阶段，质量验证的核心是**尽早发现问题**。本环节绝大部分验证动作由 CI/CD 流水线自动触发，主要通过以下手段确保代码质量：

### 1. 自动化单元测试

- **手段说明**：对最小可测试代码单元进行正确性验证，是开发者的第一道防线。
- **运作方式**：由 CI/CD 流水线在每次代码提交时自动触发执行。要求核心业务逻辑全覆盖，整体覆盖率达到目标值（≥ 80%），未达标将阻断流水线。

### 2. 代码安全与静态分析 (SAST)

- **手段说明**：通过工具扫描源代码，发现潜在的代码缺陷、规范违背及安全漏洞。
- **运作方式**：每次代码提交时，CI 自动触发增量 SAST 扫描。拦截高危问题，强制要求安全编码规范的落地。

### 3. 依赖安全扫描 (SCA)

- **手段说明**：检查项目引入的第三方开源组件及依赖库是否存在已知安全漏洞。
- **运作方式**：在依赖项发生变更时由 CI 自动触发增量扫描。确保项目中无已知的高危依赖漏洞，保障供应链安全。

### 4. 持续集成构建 (CI)

- **手段说明**：自动化编译打包，验证代码的集成与可构建性。
- **运作方式**：每次提交后自动运行，确保代码在统一环境中能够顺利编译通过，及早发现因环境或依赖导致的问题。

### 5. 代码审查 (Code Review)

- **手段说明**：开发者之间互相进行代码走查，这是本环节唯一由人工执行的验证。
- **运作方式**：在代码合并前（如 Merge Request）由人工触发并执行。审查者重点关注架构设计、代码可读性、业务逻辑正确性以及规范依从性。

## 质量门禁

进入下一环节（质量确认）前，必须通过以上验证，具体表现为：

- [ ] 代码审查（Code Review）已通过并合并
- [ ] 单元测试覆盖率达到目标值（≥ 80%）
- [ ] 增量 SAST 扫描无高危问题
- [ ] 增量 SCA 扫描无高危已知漏洞
- [ ] CI 构建全流程通过

## 关联原则

- **原则一：质量是全团队的责任** — 每位开发者对代码质量负责
- **原则五：验证前置** — 单元测试是开发者的第一道验证
- **原则六：安全是默认属性** — 安全编码从开发阶段开始

## 度量指标

| 指标           | 目标值   |
| ------------ | ----- |
| 单元测试覆盖率      | ≥ 80% |
| 代码审查覆盖率      | 100%  |
| 增量 SAST 高危问题 | = 0   |
| 构建失败率        | ≤ 5%  |
