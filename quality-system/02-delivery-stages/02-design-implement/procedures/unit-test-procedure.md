# 单元测试规程

## 1. 规程定位

本规程属于 `02-design-implement` 设计与实现环节，用于规范开发过程中单元测试的编写、维护和证据留存要求，确保核心逻辑在开发阶段完成基础验证。

单元测试是开发内建质量的一部分，不是后置检验活动。本规程不覆盖集成测试、E2E 测试等验证与准入环节的测试活动。

## 2. 适用范围

1. 适用于所有业务系统、平台服务和公共组件的开发活动。
2. 适用于新增功能、缺陷修复、重构和接口变更。
3. 不适用于纯配置变更、文档修改和不含逻辑的样式调整。
4. 前端组件中包含业务逻辑（如表单校验、状态计算）的，应编写单元测试；纯 UI 渲染组件可酌情裁剪。

## 3. 触发条件

1. 新增核心业务逻辑或领域规则。
2. 修改已有业务规则或计算逻辑。
3. 修改公共组件、工具函数或共享库。
4. 修复 P0/P1 缺陷。
5. 涉及接口契约、数据转换、权限或安全逻辑变更。
6. 重构已有代码且逻辑行为不变时，应补充或确认已有测试覆盖。

## 4. 输入

1. 已确认的需求或变更项。
2. 设计方案或技术说明。
3. 代码变更。
4. 相关编码规范和安全编码要求。
5. 历史缺陷记录（如缺陷修复场景）。

## 5. 必须动作

### 5.1 识别测试范围

1. 识别本次变更涉及的业务逻辑、公共方法和边界条件。
2. 区分必须测试的代码和可豁免的代码（如纯 getter/setter、框架生成的代码）。

### 5.2 编写单元测试

1. 每个变更必须编写对应的单元测试，覆盖正常路径和关键异常路径。
2. 缺陷修复必须编写回归测试，防止缺陷再次发生。
3. 测试用例应独立、可重复、无外部依赖（数据库、网络、文件系统）。
4. 外部依赖必须通过依赖注入或测试替身（mock/stub）隔离。
5. 测试命名应清晰表达意图，反映测试场景和预期结果。

### 5.3 执行与验证

1. 本地开发时必须执行受影响的单元测试并全部通过后，方可提交代码。
2. 提交 PR 时，单元测试必须通过 CI 流水线执行。
3. 单元测试覆盖率必须满足以下门槛：

| 代码类别 | 最低覆盖率 | 推荐覆盖率 |
|---------|-----------|-----------|
| 核心领域逻辑 | 80% | 95% |
| 业务服务层 | 70% | 85% |
| 控制器/接口层 | 50% | 70% |
| 工具类/公共函数 | 80% | 90% |

### 5.4 维护与清理

1. 已废弃的测试用例应及时清理，不得保留长期跳过（skip）的测试。
2. 临时跳过的测试必须标注原因和修复期限，且不得超过一个迭代周期。
3. 重构时同步更新受影响的测试用例，确保测试始终与代码行为一致。

## 6. 输出与证据

1. 单元测试代码（提交至代码仓库，与业务代码同仓库）。
2. 本地执行结果（开发者自行确认）。
3. CI 流水线中的单元测试执行报告和覆盖率报告。
4. 缺陷修复的回归测试用例。

## 7. 责任角色

| 角色 | 职责 |
|---|---|
| 研发工程师 | 编写、执行和维护单元测试，保证覆盖率达标 |
| 代码审查者 | 审查测试用例的充分性和质量，拒绝缺少测试的 PR |
| 技术Leader | 监督团队覆盖率趋势，对覆盖率持续不达标的情况推动改进 |
| 质量工程师 | 定期审计覆盖率数据与实际代码质量的一致性 |

## 8. 流水线验证点

| 验证点 | 名称 | 说明 |
|---|---|---|
| VP-UT-01 | 单元测试执行 | CI 流水线自动运行全部单元测试，任一失败则阻断合并 |
| VP-UT-02 | 覆盖率检查 | CI 流水线自动采集覆盖率，未达门槛则阻断合并 |
| VP-UT-03 | 跳过测试检查 | CI 流水线检测长期跳过的测试用例并告警 |

## 9. 例外与豁免

1. 紧急修复（P0 缺陷）可先提交修复代码和最小回归测试，后续补全覆盖率。
2. 技术债清理期间，对遗留代码的覆盖率要求可酌情降低，但需在迭代计划中明确补全时间。
3. 任何豁免须经技术Leader 审批，并在代码评审记录中注明。

## 10. 与其他规程的关系

- **代码审查规程**：代码审查必须包含对测试用例的审查，缺少测试的 PR 不应通过。
- **持续集成规范**：CI 流水线负责自动化执行单元测试并采集覆盖率。
- **缺陷管理规程**：缺陷修复必须附带回归测试用例。
- **测试策略**：本规程定义开发阶段的单元测试要求，集成测试和 E2E 测试由测试策略另行定义。
