# 代码静态扫描规程

## 1. 规程定位

本规程属于 `03-integrate-build` 集成与构建环节，用于规范在持续集成过程中对代码进行静态质量扫描的要求，确保代码在合并前满足质量门槛。

静态扫描在构建流水线中自动执行，聚焦代码可维护性、编码规范合规、复杂度控制和重复代码检测。本规程不覆盖安全漏洞扫描（SAST），安全扫描由安全测试规程另行定义。

## 2. 适用范围

1. 适用于所有业务系统、平台服务和公共组件的代码提交和合并请求。
2. 适用于新增功能、缺陷修复、重构和技术债务清理。
3. 不适用于纯配置变更、文档修改、自动生成代码（不含业务逻辑的部分）和第三方代码。
4. 前端、后端、移动端等项目类型均应配置相应的静态分析工具，不可因语言或框架差异而豁免。

## 3. 触发条件

1. 提交 Pull Request / Merge Request 时触发增量扫描。
2. 合并到主干分支时触发全量扫描。
3. 新增或变更静态分析规则配置后，应对当前分支执行一次全量扫描。
4. 定期的全量扫描（如每周一次），用于跟踪技术债务趋势。

## 4. 输入

1. 源代码（变更集或全量代码）。
2. 静态分析工具配置文件（如 `.sonarcloud.properties`、`.eslintrc`、`.checkstyle.xml`）。
3. 编码规范文档和团队约定的规则集。
4. 历史扫描报告（用于对比趋势）。

## 5. 必须动作

### 5.1 工具配置

1. 每个项目必须配置至少一套静态分析工具，并集成到 CI 流水线中。
2. 规则集应由技术 Leader 审批确定，兼顾行业最佳实践和团队实际情况。
3. 禁止大面积禁用规则或降低规则严重等级来绕过检查。
4. 工具配置应纳入版本控制，与源代码一同管理。

| 语言/平台 | 推荐工具（示例） |
|-----------|----------------|
| Java / Kotlin | SonarQube / SonarCloud, Checkstyle, PMD |
| JavaScript / TypeScript | ESLint, SonarQube |
| Python | Pylint, Flake8, SonarQube |
| Go | golangci-lint, SonarQube |
| C# | .NET Analyzer, SonarQube |

### 5.2 增量扫描

1. 每次提交 PR/MR 时，流水线自动对变更代码执行增量扫描。
2. 增量扫描只检查新增和修改的代码，不重复检查未变更部分。
3. 增量扫描须在 **10 分钟内**完成，避免阻塞流水线。

### 5.3 全量扫描

1. 合并到主干分支时执行全量扫描，更新项目整体质量基线。
2. 全量扫描结果作为技术债务度量的依据。
3. 全量扫描频率不低于每次主干合并。

### 5.4 质量门禁

1. 新增代码不得引入 Blocker（阻断）或 Critical（严重）等级问题。
2. 新增代码的重复率不得超过项目基线。
3. 新增代码的圈复杂度不得超过项目约定的阈值（如 Java ≤ 15，JS/TS ≤ 10）。
4. 项目整体代码覆盖率不得因本次合并而下降（与基线对比）。
5. 质量门禁未通过时，流水线应阻断合并，并给出明确的失败原因。

### 5.5 技术债务管理

1. 每次全量扫描记录技术债务比率（Technical Debt Ratio），跟踪趋势。
2. 技术债务比率超过团队约定的红线阈值时，须在迭代计划中安排清理任务。
3. 新增代码引入的技术债务应当在同一个迭代内清理。

### 5.6 规则变更管理

1. 静态分析规则的增删改应经技术 Leader 审批，并在变更记录中注明原因。
2. 规则变更后应对受影响项目重新执行全量扫描，评估影响范围。
3. 禁止在未评估影响的情况下大面积调整规则集。

## 6. 输出与证据

1. 增量扫描报告（关联到对应的 PR/MR）。
2. 全量扫描报告（关联到对应的构建记录）。
3. 质量门禁检查结果（通过/阻断/告警）。
4. 技术债务趋势图或报告（定期生成）。
5. 静态分析工具配置文件（纳入版本控制）。

## 7. 责任角色

| 角色 | 职责 |
|------|------|
| 研发工程师 | 修复扫描发现的问题，确保新增代码通过质量门禁 |
| 代码审查者 | 审查 PR 时关注静态扫描结果，对规避检查的行为提出质疑 |
| 技术 Leader | 审批规则集配置，监督技术债务趋势，对持续不达标的情况推动改进 |
| DevOps 工程师 | 维护静态分析工具的集成和配置，确保工具稳定运行 |

## 8. 流水线验证点

| 验证点 | 名称 | 说明 |
|--------|------|------|
| VP-SA-01 | 增量扫描执行 | CI 流水线自动执行增量静态扫描，阻断含 Blocker/Critical 问题的合并 |
| VP-SA-02 | 质量门禁检查 | CI 流水线检查新增代码的复杂度、重复率等指标是否达标 |
| VP-SA-03 | 技术债务趋势 | 定期报告项目技术债务比率变化趋势 |

## 9. 例外与豁免

1. 紧急修复（P0 缺陷）可先合并代码，事后补充修复扫描问题，但修复期限不得超过 24 小时。
2. 遗留代码的全量扫描问题不作为合并阻断条件，但新改动的代码仍需满足增量门禁。
3. 第三方代码（如生成的 protobuf 代码、OpenAPI 生成的客户端）可配置排除规则。
4. 任何规则豁免须经技术 Leader 审批，并在项目静态分析配置中备注说明。

## 10. 与其他规程的关系

- **安全测试规程**：本规程不重复安全扫描（SAST），安全静态扫描由安全测试规程覆盖。
- **代码审查规程**：代码审查应结合静态扫描结果进行，审查者有权要求开发者修复扫描发现问题。
- **持续集成规范**：CI 流水线负责触发增量扫描和全量扫描，质量门禁结果是合并准入条件之一。
- **单元测试规程**：静态扫描关注代码结构和质量，单元测试关注逻辑正确性，二者互为补充。
