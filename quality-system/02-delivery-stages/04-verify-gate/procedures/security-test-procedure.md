# 安全测试规程

## 目的

识别和验证系统中的安全漏洞，确保产品在发布前满足安全要求。

## 适用范围

- 每次版本发布前的安全验证
- 安全敏感功能变更后的专项测试
- 定期安全扫描

## 职责

| 角色 | 职责 |
|------|------|
| 质量工程师 | 执行 SAST/DAST 扫描、编写安全测试用例 |
| 安全负责人 | 审批安全测试计划、评估漏洞风险 |
| 开发者 | 修复安全漏洞、配合安全测试 |

## 安全测试类型

### SAST（静态应用安全测试）

- **工具**：SonarQube / Semgrep / Snyk Code
- **执行时机**：
  - **增量扫描**：每次代码提交（CI 集成）—— 归属开发构建环节
  - **全量扫描**：发布前 —— 归属质量确认环节
- **执行者**：CI 自动
- **自动化**：**自动**
- **扫描范围**：全部源代码
- **关注点**：
  - SQL 注入
  - XSS（跨站脚本）
  - 硬编码密钥和凭证
  - 不安全的反序列化
  - 路径遍历

### DAST（动态应用安全测试）

- **工具**：OWASP ZAP / Burp Suite
- **执行时机**：发布前、重大功能变更后
- **执行者**：CI 自动
- **自动化**：**自动**
- **扫描范围**：运行中的应用
- **关注点**：
  - 认证和会话管理漏洞
  - 授权绕过
  - 敏感数据暴露
  - CSRF（跨站请求伪造）
  - 不安全的 HTTP 头

### SCA（软件成分分析）

- **工具**：Snyk / Trivy / Dependabot / OWASP Dependency-Check
- **执行时机**：
  - **增量扫描**：每次依赖变更（CI 集成）—— 归属开发构建环节
  - **全量扫描**：发布前 —— 归属质量确认环节
- **执行者**：CI 自动
- **自动化**：**自动**
- **扫描范围**：第三方直接依赖及传递依赖
- **关注点**：
  - 已知漏洞（CVE）
  - 过时依赖
  - 许可证合规

#### CVE 严重等级与修复时效

| CVE 等级 | CVSS 评分 | CI 阻断规则 | 修复 SLA | 修复后要求 |
|----------|-----------|------------|---------|-----------|
| 紧急 (Critical) | ≥ 9.0 | 阻断合并 | ≤ 24 小时 | 须发 patch 版本修复 |
| 高危 (High) | 7.0 - 8.9 | 阻断合并 | ≤ 7 天 | 须在下一个迭代修复 |
| 中危 (Medium) | 4.0 - 6.9 | 告警，不阻断 | ≤ 30 天 | 按计划排期修复 |
| 低危 (Low) | < 4.0 | 记录，不告警 | ≤ 90 天 | 纳入技术债务跟踪 |

- 增量扫描：发现 Critical/High 等级 CVE 时阻断合并，将 CVE 编号和受影响组件信息回写到 PR 评论。
- 全量扫描：生成完整的 CVE 报告，包括所有已知漏洞的清单、影响范围和修复建议。

#### CVE 数据库来源

SCA 工具应至少对接以下一个或多个 CVE 数据库：

- **NVD（National Vulnerability Database）**：美国国家漏洞数据库，CVE 的官方来源。
- **GitHub Advisory Database**：GitHub 维护的 CVE 数据库，与 Dependabot 集成。
- **GitLab Advisory Database**：GitLab 维护的安全公告数据库。
- **OSV（Open Source Vulnerabilities）**：Google 维护的开源漏洞数据库。

#### CVE 误报处理

1. 经人工确认不属于实际漏洞的 CVE，可在 SCA 工具中标记为误报（wontfix）。
2. 误报标记必须附上人工确认的理由说明（如：该漏洞路径在实际运行中不可达）。
3. 误报标记须经安全负责人审批。
4. 误报清单应定期复审（至少每季度一次），确认新版本中是否已修复或状态是否变化。

#### CVE 修复策略

1. 优先通过升级依赖版本修复 CVE。
2. 无法升级时（如破坏性变更），评估补丁（patch）或临时缓解措施（如 WAF 规则、配置变更）。
3. 使用临时缓解措施的，须在工单系统中记录缓解方案和后续修复计划。
4. 依赖已停止维护且无法替换的，须经安全负责人评估残留风险并书面审批。

### 渗透测试

- **执行方**：外部安全团队或专业安全工程师
- **执行时机**：重大版本发布前、年度安全审计
- **执行者**：外部安全团队
- **自动化**：**手动**
- **范围**：完整应用系统
- **关注点**：
  - 业务逻辑漏洞
  - 权限提升
  - 数据泄露路径

## 漏洞等级

| 等级 | CVSS 评分 | 修复时效 | 示例 |
|------|----------|---------|------|
| 高危 | ≥ 7.0 | ≤ 24 小时 | SQL 注入、未授权数据访问 |
| 中危 | 4.0 - 6.9 | ≤ 7 天 | 存储型 XSS、不安全的直接对象引用 |
| 低危 | < 4.0 | ≤ 30 天 | 信息泄露、不安全的 HTTP 头 |

## 流程

### 1. 安全测试计划

- 确定测试范围和类型
- 识别安全敏感功能
- 定义测试环境
- 安排测试时间

### 2. 执行安全扫描

| 扫描类型 | 执行者 | 自动化 | 执行时机 | 归属环节 |
|---------|--------|--------|---------|---------|
| 增量 SAST | CI 自动 | **自动** | 每次提交 | 开发构建 |
| 全量 SAST | CI 自动 | **自动** | 发布前 | 质量确认 |
| 增量 SCA | CI 自动 | **自动** | 依赖变更时 | 开发构建 |
| 全量 SCA | CI 自动 | **自动** | 发布前 | 质量确认 |
| DAST | CI 自动 | **自动** | 发布前 | 质量确认 |
| 渗透测试 | 外部安全团队 | **手动** | 重大版本/年度 | 质量确认 |

### 3. 漏洞评估

- 对发现的漏洞进行等级评定
- 评估业务影响
- 确定修复优先级
- 记录到缺陷管理系统

### 4. 漏洞修复

- 按修复时效要求完成修复
- 修复方案需经安全负责人审查
- 高危漏洞修复需专项验证

### 5. 回归验证

- 修复后重新执行相关安全测试
- 确认漏洞已修复且未引入新问题
- 验证通过后关闭缺陷

### 6. 安全测试报告

报告包含：

1. 测试范围和方法
2. 发现的漏洞清单（等级、描述、影响）
3. 修复状态
4. 残留风险评估
5. 发布建议

## 发布安全门禁

发布前须满足：

- [ ] 全量 SAST 扫描无高危问题
- [ ] 全量 SCA 无高危已知漏洞
- [ ] DAST 扫描完成，高危漏洞已修复
- [ ] 渗透测试已执行（如触发条件满足）
- [ ] 安全测试报告已审批

## 安全合规要求

教育行业产品须特别关注：

- **个人信息保护法**：学生数据收集、存储、使用的合规性
- **数据安全法**：教育数据的分类分级和安全管理
- **未成年人保护**：未成年人信息的特殊保护措施

## 度量

| 指标 | 目标值 |
|------|--------|
| 高危漏洞修复时效 | ≤ 24 小时，达标率 100% |
| 中危漏洞修复时效 | ≤ 7 天，达标率 100% |
| 发布时高危漏洞数 | = 0 |
| 安全测试覆盖率 | 核心功能 100% |
