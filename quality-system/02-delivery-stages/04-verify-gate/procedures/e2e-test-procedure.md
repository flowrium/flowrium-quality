# E2E 测试规程

## 目的

从用户视角验证完整业务流程，确保系统作为一个整体能够正确地支撑用户操作。

## 适用范围

- 核心业务流程的端到端验证
- 关键用户路径的完整性验证
- 跨系统交互场景验证

## 职责

| 角色 | 职责 |
|------|------|
| 质量工程师 | 编写和维护 E2E 测试用例、执行测试 |
| 产品经理 | 确认核心业务流程和验收标准 |
| 开发者 | 协助定位问题、修复缺陷 |

## 流程

### 1. 识别测试场景

从以下来源识别 E2E 测试场景：

- **用户故事**：每个用户故事对应至少一个 E2E 场景
- **业务流程**：核心业务流程必须覆盖（P0 场景 100%）
- **关键路径**：用户最常用的操作路径
- **风险场景**：历史缺陷高发区域

### 2. 优先级划分

| 优先级 | 定义 | 覆盖要求 |
|--------|------|---------|
| P0 | 核心业务流程，阻断性场景 | 100% 覆盖 |
| P1 | 重要用户路径，高影响场景 | ≥ 80% 覆盖 |
| P2 | 辅助功能，低频场景 | 按需覆盖 |

### 3. 编写测试用例

按 [测试用例模板](test-case-template.md) 编写，E2E 测试用例须包含：

- **前置条件**：用户状态、数据准备、系统配置
- **操作步骤**：用户操作序列（含页面交互）
- **预期结果**：每步操作后的系统响应和状态
- **后置清理**：测试数据清理

### 4. 自动化

- P0 场景必须自动化
- P1 场景推荐自动化
- 使用 Page Object 模式组织代码
- 测试数据与测试代码分离

### 5. 执行

| 触发条件 | 执行范围 |
|---------|---------|
| 发布前 | 全量 E2E 测试 |
| 每日构建 | P0 + P1 自动化场景 |
| 代码合并 | P0 自动化场景（冒烟测试） |

### 6. 结果处理

- 失败用例分析根因：环境问题 / 测试代码问题 / 产品缺陷
- 产品缺陷按 [缺陷管理规程](defect-management-procedure.md) 处理
- 环境问题记录并修复测试环境
- 测试代码问题修复后重新执行

## 测试数据管理

- 每个测试用例使用独立的测试数据
- 测试数据可重复创建和清理
- 敏感数据使用脱敏处理
- 测试数据通过脚本或 Fixture 管理

## 环境

E2E 测试在 Staging 环境执行，该环境：

- 与生产环境架构一致
- 使用独立的测试数据库
- 外部服务使用沙箱环境
- 测试后可重置到初始状态

## 度量

| 指标 | 目标值 |
|------|--------|
| P0 场景覆盖率 | 100% |
| E2E 测试通过率 | ≥ 98% |
| E2E 自动化率 | P0 100%，整体 ≥ 60% |
