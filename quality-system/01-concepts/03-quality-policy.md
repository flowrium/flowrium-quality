# 质量政策

## 1. 政策定位

质量政策是组织层面对软件质量管理的基本要求。

质量政策连接质量价值观与具体规程，是质量体系执行和审计的依据。

## 2. 总体政策

组织应建立并持续改进软件质量管理体系，确保软件产品和交付过程能够持续满足业务目标、用户需求、安全要求、合规要求和运行稳定性要求。

质量管理不应仅依赖最终测试，而应贯穿需求、设计、实现、集成、验证、发布、运行和反馈全过程。

## 3. 需求质量政策

1. 所有需求和变更必须有明确来源。
2. 进入开发前的需求应具备清晰描述。
3. 需求应具备可验证的验收标准。
4. 高风险需求应完成风险和影响评估。
5. 需求应能够追溯到代码、测试和发布。

## 4. 设计质量政策

1. 中高复杂度变更应进行方案设计。
2. 架构影响变更应进行架构评审。
3. 设计应优先保持简单、清晰、可维护。
4. 设计应考虑安全、性能、扩展性和可运维性。
5. 设计决策应保留必要记录。

## 5. 开发质量政策

1. 开发人员对代码质量负直接责任。
2. 代码提交前应完成必要自检。
3. 关键逻辑应具备单元测试。
4. 代码合并前应经过评审。
5. 依赖、配置、接口变更应有记录。

## 6. 构建质量政策

1. 共享分支上的代码应能够持续集成。
2. 构建过程应尽可能自动化。
3. 构建产物应具有版本标识。
4. 构建产物应可追溯到源码和变更。
5. 构建失败应及时处理。

## 7. 验证质量政策

1. 版本候选发布前应完成必要验证。
2. 测试范围应与变更范围和风险等级匹配。
3. 严重缺陷不得未经处理直接发布。
4. 安全阻断项不得未经审批直接发布。
5. 质量门禁结论应有证据支撑。

## 8. 发布质量政策

1. 发布必须受控。
2. 发布前应具备发布说明。
3. 发布前应明确影响范围和风险。
4. 发布后应完成冒烟验证。
5. 关键系统发布应具备回滚或恢复方案。

## 9. 运行质量政策

1. 生产系统应具备必要监控。
2. 关键服务应具备告警机制。
3. 生产事件应记录和分级。
4. 严重事件应进行复盘。
5. 运行反馈应进入改进闭环。

## 10. 改进质量政策

1. 质量体系应定期回顾。
2. 缺陷、事故、客户反馈应驱动体系改进。
3. 改进项应有责任人和完成期限。
4. 改进结果应被验证。
5. 规程和模板应随着实践持续更新。
