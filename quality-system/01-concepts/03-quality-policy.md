# 质量政策

## 1. 政策定位

质量政策是组织层面对软件质量管理的基本要求。

质量政策连接质量价值观与具体规程，是质量体系执行和审计的依据。

## 2. 总体政策

组织应建立并持续改进软件质量管理体系，确保软件产品和交付过程能够持续满足业务目标、用户需求、安全要求、合规要求和运行稳定性要求。

质量管理不应仅依赖最终测试，而应贯穿需求、设计、实现、集成、验证、发布、运行和反馈全过程。

## 3. 适用性与风险分级

1. 本质量政策默认适用于所有软件产品、平台、工具、服务和交付项目。
2. 项目可根据业务影响、数据敏感性、系统关键性、技术复杂度和变更规模进行低、中、高风险分级。
3. 不同风险等级可以采用不同执行深度，但不得删除关键质量责任、关键风险控制和必要证据。
4. 高风险项目不得绕过安全、数据、发布审批、可追溯证据和事故响应相关控制。
5. 裁剪或放宽政策要求时，应按照治理规则和例外豁免机制进行记录、审批和复盘。

## 4. 需求质量政策

1. 所有需求和变更必须有明确来源。
2. 进入开发前的需求应具备清晰描述。
3. 需求应具备可验证的验收标准。
4. 高风险需求应完成风险和影响评估。
5. 需求应能够追溯到代码、测试和发布。

## 5. 设计质量政策

1. 中高复杂度变更应进行方案设计。
2. 架构影响变更应进行架构评审。
3. 设计应优先保持简单、清晰、可维护。
4. 设计应考虑安全、性能、扩展性和可运维性。
5. 设计决策应保留必要记录。

## 6. 开发质量政策

1. 开发人员对代码质量负直接责任。
2. 代码提交前应完成必要自检。
3. 关键逻辑应具备单元测试。
4. 代码合并前应经过评审。
5. 依赖、配置、接口变更应有记录。

## 7. 构建质量政策

1. 共享分支上的代码应能够持续集成。
2. 构建过程应尽可能自动化。
3. 构建产物应具有版本标识。
4. 构建产物应可追溯到源码和变更。
5. 构建失败应及时处理。

## 8. 验证质量政策

1. 版本候选发布前应完成必要验证。
2. 测试范围应与变更范围和风险等级匹配。
3. 严重缺陷不得未经处理直接发布。
4. 安全阻断项不得未经审批直接发布。
5. 质量门禁结论应有证据支撑。

## 9. 发布质量政策

1. 发布必须受控。
2. 发布前应具备发布说明。
3. 发布前应明确影响范围和风险。
4. 发布后应完成冒烟验证。
5. 关键系统发布应具备回滚或恢复方案。

## 10. 运行质量政策

1. 生产系统应具备必要监控。
2. 关键服务应具备告警机制。
3. 生产事件应记录和分级。
4. 严重事件应进行复盘。
5. 运行反馈应进入改进闭环。

## 11. 改进质量政策

1. 质量体系应定期回顾。
2. 缺陷、事故、客户反馈应驱动体系改进。
3. 改进项应有责任人和完成期限。
4. 改进结果应被验证。
5. 规程和模板应随着实践持续更新。

## 12. 编码方式与工具质量政策

1. 质量体系关注最终输出代码、测试、制品和证据的质量，不限定代码由人工编写、工具辅助生成或其他方式产生。
2. 任何代码、测试、配置、文档或验证结论都必须有明确责任人，不得以工具输出替代质量责任。
3. 工具辅助编码、自动化生成和自动化验证不得绕过代码评审、测试验证、安全检查、发布审批和证据留存。
4. 涉及安全、数据、合规、架构和关键业务逻辑的输出，应进行人工复核和必要验证。
5. 编码和验证方式中的缺陷、误用和有效经验应进入反馈改进闭环。
