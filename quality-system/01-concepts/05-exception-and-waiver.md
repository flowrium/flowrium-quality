# 例外与豁免机制

## 1. 机制定位

质量体系允许在特殊情况下进行例外处理或豁免，但所有例外和豁免必须受控。

例外与豁免机制的目的不是绕过质量要求，而是在紧急、特殊或低风险场景下，以可追溯、可审批、可复盘的方式管理偏离。

## 2. 基本原则

1. 豁免必须有理由。
2. 豁免必须有责任人。
3. 豁免必须有审批。
4. 豁免必须有记录。
5. 豁免必须有有效期。
6. 高风险豁免必须有补救措施。
7. 豁免不应成为常态。

## 3. 可申请豁免的场景

以下情况可以申请豁免：

1. 紧急生产修复。
2. 重大客户阻断问题。
3. 监管或业务强制时限要求。
4. 低风险内部工具变更。
5. 已有等效验证手段。
6. 当前工具能力暂不支持自动化验证。
7. 非核心路径的临时性变更。

## 4. 不允许豁免的场景

以下情况原则上不允许豁免：

1. 明知存在严重安全漏洞仍发布。
2. 明知存在数据破坏风险仍发布。
3. 未经授权访问生产数据。
4. 绕过发布审批直接上线核心系统。
5. 删除或伪造质量证据。
6. 规避审计要求。
7. 未经批准跳过高风险变更评审。

## 5. 豁免信息要求

每个豁免记录至少包含：

| 字段 | 说明 |
|---|---|
| 豁免编号 | 唯一标识 |
| 申请人 | 提出豁免的人 |
| 所属项目 | 豁免影响的项目 |
| 豁免对象 | 被豁免的规程、门禁或要求 |
| 豁免原因 | 为什么需要豁免 |
| 风险说明 | 豁免带来的风险 |
| 补救措施 | 后续如何补偿 |
| 有效期 | 豁免何时失效 |
| 审批人 | 谁批准该豁免 |
| 复盘要求 | 是否需要后续复盘 |

## 6. 豁免流程

```text
提出豁免申请
  ↓
说明原因和风险
  ↓
责任角色评估
  ↓
审批人批准或拒绝
  ↓
记录豁免证据
  ↓
执行变更
  ↓
补救或复盘
  ↓
关闭豁免
```
